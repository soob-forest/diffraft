## 유지할 점

- 선택 승인·거절·단위 전체 의견을 별도 행동으로 분리하고 저장 효과를 안내한다.
- 거절 재검토, 초안 보관, 반복 입력 보호와 다음 제목 포커스는 안전한 반복 검토를 돕는다.

## 우선순위 문제

### 1. [P1] 도구가 본문 높이를 차지해 읽기와 결정이 갈라진다

`1280-1.png`에는 진척, 선택 제목·종류, 선택기·행동, 이유, 직전 결과, 비교 레이블이 쌓인다. 현재 뷰포트에는 삭제행이 보이지만 대응하는 추가행은 아래에 있다. 작은 창과 확대 상태에서 본문을 읽는 위치로 이동하면 결정 도구가 화면 밖이 된다. 영구적인 접근 불가가 아니라 반복 스크롤과 재확인 비용의 문제다.

근거: `UnitReviewTools.tsx:172`, `UnitReviewTools.tsx:207`, `UnitReview.tsx:157`, `UnitReviewDiff.tsx:100`, `compact-layout.css:54`.

대안: 헤더 전체 고정은 변경이 작지만 큰 도구가 계속 화면을 점유한다. 선택 제목·이전/다음·승인/거절만 짧은 고정 행으로 두면 본문을 확보할 수 있으나 보조 안내를 이동해야 한다. 후자를 권장한다. 제목과 선택기를 합치고 반복 이유·직전 결과의 상시 높이를 줄인다. 코멘트 패널을 열었을 때도 본문 읽기 공간을 확보한다.

후속 작업: `$impeccable layout`, `$impeccable adapt`.

### 2. [P1] 선택 단위와 읽는 변경의 연결이 약하다

원래 전체 후보는 여러 변경을 포함하므로 선택 변경2와 본문 변경3이 동시에 보일 수 있다. 이것은 데이터 오류가 아니지만, 상단의 짧은 `승인` 버튼이 어느 변경을 처리하는지 매번 기억으로 대조하게 만든다. 선택의 시각적 차이는 주로 변경 제목의 청색에 집중돼 있다.

근거: `review-layout.css:205`, `decorations.ts:143`, `UnitReviewTools.tsx:232`, `1440-1-processed.png`, `1280-1-processed.png`.

대안: 스크롤에 따라 선택을 바꾸면 보는 위치와 맞지만 승인 대상이 뜻하지 않게 달라질 수 있다. 명시적 선택을 유지하면서 해당 단위의 모든 관련 범위에 번호·좌측 표식을 두는 쪽이 기존 안전 계약을 지킨다. 후자를 권장한다. `변경 3 승인`처럼 대상을 버튼에 표시하고, 선택 범위가 화면 밖일 때만 구체적인 이동 안내를 제공한다.

후속 작업: `$impeccable clarify`, `$impeccable harden`.

### 3. [P2] 필터·선택기·이전/다음의 탐색 범위가 다르다

왼쪽 목록은 미처리/처리됨/전체를 필터링하지만 중앙 선택기는 전체 단위를 표시한다. 이전/다음은 필터 결과를 순회하고 비면 전체로 대체한다. 필터를 처리됨으로 바꿔도 중앙은 기존 미처리 선택과 승인 행동을 유지할 수 있어 목록에 현재 선택이 사라진다. 처리 단위 선택은 원래 전체 후보 비교로도 전환된다.

근거: `useUnitNavigation.ts:21`, `:25`, `:81`, `:97`, `UnitReviewNavigation.tsx:31`, `UnitReviewTools.tsx:50`.

대안: 항상 전체 번호 순서를 쓰면 단순하지만 미처리만 넘기는 효율이 줄어든다. 공통 필터를 모든 탐색에 적용하면 범위는 명확해지지만 필터 변경 시 선택 규칙을 정해야 한다. 공통 필터를 권장한다. `다음 미처리 변경`처럼 범위를 표시하고, 목록이 보일 때는 중앙 선택기를 합치거나 생략한다. 필터 밖 선택을 유지한다면 별도 표시하고, 아니면 첫 유효 단위로 명시 이동한다.

후속 작업: `$impeccable distill`, `$impeccable clarify`.

### 4. [P2] 초안 보관과 코멘트 등록 상태가 여러 문구로 흩어진다

작성 중 안내, 초안 저장 상태, 저장된 코멘트 수, 등록 오류가 각각 표시된다. 초안 저장은 성공했지만 의견 등록은 실패한 경우 무엇이 안전하게 보관됐는지 여러 위치를 읽어 판단해야 한다.

근거: `UnitComments.tsx:103`, `UnitComments.tsx:134`, `UnitComments.tsx:137`, `1440-1-comment.png`, `1440-1-error.png`.

대안: 두 상태 배지를 상시 병렬 노출하면 의미는 분명하지만 정보량이 늘어난다. 버튼 가까이 현재 등록 결과와 실제 보관 여부를 한 문장으로 요약하는 안을 권장한다. 예: `코멘트 등록 실패 · 입력은 초안으로 보관돼 있습니다`. 보관 성공을 확인한 경우에만 이 문구를 사용한다. 복구 가능한 오류에는 `다시 저장`, 재실행이 필요한 경우에는 이유와 복구 경로를 표시한다.

후속 작업: `$impeccable clarify`, `$impeccable harden`.

### 5. [P2] 텍스트 읽기의 발견성과 비교 기준이 본문과 어긋난다

본문의 삭제·추가 기호는 CodeMirror gutter에 있고 gutter는 접근성 트리에서 숨겨진다. 행 본문에는 변경 종류를 알리는 의미가 없다. 다만 `작업 옵션 → 텍스트로 변경 읽기`라는 대체 경로는 존재하므로 대체 읽기 기능이 없다고 판단해서는 안 된다.

원래 전체 후보 본문은 `original.value`를 사용하는 반면, 작업 옵션의 TextDiff는 계속 현재 `panel.review.projection.hunks`를 받는다. 승인·거절 이후 두 비교가 달라진 경우 시각 본문과 대체 읽기가 다른 변경을 설명할 수 있다. 이는 props 경로로 확인한 조건부 불일치이며 실제 VoiceOver 발화는 미검증이다.

근거: `UnitReviewDiff.tsx:43`, `UnitReviewDiff.tsx:67`, `ReviewTaskOptions.tsx:26`, `decorations.ts:69`, `decorations.ts:93`, 설치된 `@codemirror/view/dist/index.js:11493`.

대안: CodeMirror 각 행에 직접 의미를 넣으면 본문 내 읽기를 개선하지만 구현·발화 검증 범위가 크다. 현재 표시 중인 projection을 기존 TextDiff에도 전달하고 비교 영역에서 읽기 진입을 드러내는 안이 더 작다. 후자를 우선 권장한다.

후속 작업: `$impeccable harden`, `$impeccable clarify`.
