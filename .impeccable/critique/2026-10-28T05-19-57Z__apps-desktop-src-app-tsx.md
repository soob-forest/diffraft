# DocReview 사용성 분석 및 UI/UX 개선 계획

작성일: 2026-10-28 · 대상: 현재 데스크톱 앱 0.1.0 · 검토 모드: Operate

Method: dual-agent — A: `/root/design_review` · B: `/root/design_detector`

## 1. 결론

현재 제품의 우선 과제는 **AI 요청과 변경 승인을 찾고 실행하는 비용을 줄이는 것**이다. 문서·제안·대화를 분리하는 제품 구조는 적절하지만, 자주 수정하지 않는 조건 폼이 요청 입력보다 앞에 있고, 요청 범위와 실행 위치가 떨어져 있으며, 읽는 diff와 승인 행동도 분리되어 있다.

기존 문서 중심 구조를 유지하면서 ① 요청 입력의 우선순위 ② 요청 범위의 가시성 ③ 비교와 결정의 근접성을 먼저 개선한다. 장식이나 브랜드 변경보다 반복 작업의 효율과 판단의 정확성을 우선한다. 검토 자료에서 작업 완료를 불가능하게 하는 P0 문제는 확인하지 못했다.

### 3.1 Impeccable 적용 결과

`impeccable context`를 1회 실행하고 `critique` 플레이북을 적용했다. PRODUCT.md·DESIGN.md는 없으며, 기존 제품의 범위가 정해진 평가이므로 현재 구현과 제품 문서를 기준으로 진행했다. 컨텍스트 파일 생성이나 디자인 체계 정비는 이번 범위에 추가하지 않는다.

평가 A는 디자인·인지 부하·페르소나를 검토했고, 평가 B는 A 결과를 보지 않고 별도로 소스 검사를 실행했다. A 완료 후 B를 실행했다.

| 검사 | 결과와 해석 |
| --- | --- |
| 명령 | `impeccable detect --json apps/desktop/src` |
| 결과 | 종료 코드 2, warning 1건, category `slop`, rule `side-tab` |
| 위치 | `apps/desktop/src/review/review.css:202`의 `border-left: 3px solid #abc0df` |
| 수동 판단 | `.review-panel blockquote`의 인용 경계선이다. 코멘트 대상 원문·인용 구간을 구분하는 의미가 있어 장식성 위반으로는 오탐으로 분류한다. 제거 대상으로 올리지 않는다. |
| 한계 | 이 결과는 접근성·시각 대비·성능 통과를 의미하지 않는다. |

macOS Tauri의 WKWebView에는 플레이북의 CDP 부착 경로를 적용할 수 없고 이 세션의 native computer API도 비활성화되어, 실시간 앱 검사·overlay 주입은 수행하지 않았다. 현재 소스와 실제 앱 캡처를 대체 근거로 사용했다.

### 유지할 강점

1. 실제 텍스트 diff, 줄 내부 강조, −/+ 기호, 인라인·나란히·텍스트 대안이 변경 이해를 돕는다.
2. 미승인 제안과 확정본이 분리되고, 요청·전체 적용·내보내기에서 결과 범위를 설명한다.
3. 자동 저장·생성 중단·실패 후 재요청·버전 복원이 있어 사용자가 시도를 통제할 수 있다.

## 5. 디자인 검토

### 5.1 제품 고유성과 시각 방향

확정본·제안·작업 대화를 분리한 구성은 제품 목적에 맞는다. 절제된 청색·중립 배경과 변경 색상도 검토 도구에 적절하다. 다만 주요 행동보다 조건 입력 폼이 먼저 눈에 들어오고, 일반 버튼의 비슷한 무게가 요청·승인·복구의 차이를 약하게 만든다.

기존 시각 정체성을 보존하면서 문서 읽기와 결정에 공간을 배정한다. 주요 행동의 강조, 선택 변경의 명시, 조건의 점진적 공개가 우선이다. 새 색상·애니메이션·카드 장식은 해결의 전제조건이 아니다.

### 5.3 인지 부하와 페르소나

시각적 위계, 한 번에 하나의 결정, 선택지 절제, 기억 의존 최소화, 점진적 공개 등 5개 항목에 개선이 필요하다. 기본 영역 그룹화는 장점이고 공통 조건·후보 수정 등의 접기는 이미 활용한다. 문서 헤더에는 모드 3개와 저장·복구·내보내기가, 변경 도구에는 그룹 버튼과 이전·다음·전체 승인이 함께 노출된다. 버튼 수 자체보다 목적별 위계를 먼저 고친다.

## 6. 개선 우선순위와 대안

P1은 핵심 흐름에 큰 혼란·반복 비용을 주는 문제, P2는 우회할 수 있으나 개선이 필요한 문제다. 우선순위는 빈도 추정과 핵심 여정 영향에 따른 것이며 사용자 데이터로 재조정한다.

### UX-01 · P1 · AI 요청이 조건 폼 아래에 숨는다

- **확인 사실:** TaskPanel은 TaskForm 다음에 GenerationPanel을 렌더링한다. 목표 3행·고정 조건 5행과 조건 저장 버튼이 상시 표시된다. [편집 캡처](docs/usage/images/workspace.png) 첫 화면에 요청 실행 버튼이 보이지 않는다.
- **영향 가설:** 첫 사용자는 설정을 끝내는 것이 주 작업으로 보이고, 반복 사용자는 조건 영역을 계속 지나야 한다. 작업이 없으면 요청 폼 자체가 없어 다음 행동을 놓칠 수 있다.
- **개선:** 기존 작업은 목표·조건을 짧게 요약하고 필요할 때 편집한다. 요청 입력·실행을 우선 배치한다. 새 작업에서는 “작업을 만들면 AI 요청을 시작할 수 있습니다”와 생성 행동을 함께 제공한다.
- **대안 A:** 폼 높이만 줄임 — 장점: 변경 작음 / 단점: 긴 조건에서 재발 / 위험: 입력 가독성 저하.
- **대안 B, 선택:** 조건 요약+펼쳐 편집 — 장점: 반복 사용 공간 확보 / 단점: 편집에 한 단계 추가 / 위험: 미저장 조건을 놓칠 수 있어 저장 상태 표시 필요.
- **완료 조건:** 기존 작업의 첫 화면에서 요청 입력과 실행에 접근할 수 있고, 조건 변경·실패·작업 전환 시 기존 저장 계약을 유지한다. 신규 작업의 다음 단계도 분명해야 한다.
- **Impeccable 후속:** `distill`, `onboard`, `layout`.

### UX-02 · P1 · 비교 내용과 선택 승인·거절이 떨어져 있다

- **확인 사실:** ReviewBody는 DiffViewer 뒤에 ProposalDetails를 렌더링한다. [review.css](apps/desktop/src/review/review.css)의 diff 높이는 330px이고 검토 패널과 편집기에 별도 스크롤이 있다. 전체 승인은 diff 위, 선택 승인은 아래다. [검토 캡처](docs/usage/images/change-review.png)에서도 확인된다.
- **영향 가설:** 변경을 읽은 뒤 결정 버튼으로 이동하며 대상 변경을 다시 확인해야 한다. 그룹이 많으면 GroupNavigation의 모든 버튼이 도구 영역 높이를 늘린다.
- **개선:** 선택 그룹 번호·제목·승인·거절을 비교 내용과 함께 유지하는 도구 영역을 둔다. diff는 남은 높이를 사용하도록 조정한다. 전체 승인은 보조 행동으로 분리하고 독립 승인 그룹 개수를 표시한다.
- **대안 A:** 변경마다 버튼 반복 — 장점: 대상 가까움 / 단점: 긴 문서에 반복 UI 증가 / 위험: 복잡한 그룹 경계 오인.
- **대안 B, 선택:** 선택 그룹의 고정 도구 영역 — 장점: 기존 그룹 모델 유지 / 단점: 선택 상태를 분명히 보여야 함 / 위험: 화면에 보이는 변경과 선택 변경의 불일치.
- **완료 조건:** 긴 diff를 읽는 동안 현재 승인 대상과 행동이 함께 보인다. 보기 전환·선택 이동 후 대상이 정확하고 결합 그룹은 한 단위로 처리한다. 줄 수·그룹 수·내부 제안 수는 혼용하지 않는다.
- **Impeccable 후속:** `layout`, `clarify`.

### UX-03 · P1 · 요청 범위와 실행 위치가 분산되어 있다

- **확인 사실:** ScopeBar는 중앙 원문 아래, 요청 폼은 오른쪽에 있다. GenerationPanel도 원문 아래에서 범위를 정하라고 안내한다. 전체 재작성은 변경 검토 안 RewriteForm으로 이동해야 한다.
- **정확성:** `범위 확인`은 요청 필수 단계가 아니다. prepareRequest가 원문 저장 후 최신 범위를 다시 계산한다. 문제는 수동 확인 UI가 필수 단계처럼 읽히고 실행 시점의 범위가 멀리 있다는 점이다.
- **개선:** 요청 폼 가까이에 전체 문서·섹션명·선택 범위 요약과 수정 진입점을 제공한다. 일반 수정·설명과 함께 전체 재작성도 발견할 수 있게 하되, 전체 전달 확인과 전체 적용 규칙은 유지한다.
- **대안 A:** 양쪽에 범위 제어 복제 — 장점: 접근 지점 증가 / 단점: 중복 UI / 위험: 표시·선택 동기화 혼란.
- **대안 B, 선택:** 요청 근처 단일 범위 제어와 요약 — 장점: 실행 맥락 일치 / 단점: 기존 배치 변경 / 위험: 포커스 이동 때 원문 선택이 사라지지 않게 검증 필요.
- **완료 조건:** 확인창을 열기 전에도 대상 범위를 알 수 있다. 빈 선택을 전체 문서로 확대하지 않고, 본문 변경 시 기존 확인을 무효화한다. 실제 전송 원문과 요약이 일치해야 한다.
- **Impeccable 후속:** `clarify`, `shape`.

### UX-04 · P2 · 좁은 창에서 문서 공간을 조절하기 어렵다

- **확인 사실:** [Tauri 설정](apps/desktop/src-tauri/tauri.conf.json)은 최소 800×600을 허용한다. [editor.css](apps/desktop/src/editor/editor.css)는 950px 이하에서 작업 패널을 문서 아래로 보낸다. 보조 패널 접기는 없고 DiffViewer는 열 폭 안내 없이 나란히 보기를 제공한다.
- **영향 가설:** 작은 창에서 요청 발견성이 낮아지고 비교 문장이 과도하게 줄바꿈될 수 있다. 실제 최소 창의 잘림·조작 실패는 미실측이다. 디자인 명세의 권장 1280×800과 실제 허용 최소 크기를 구분해야 한다.
- **대안 A:** 최소 창 크기 상향 — 장점: 단순 / 단점: 작은 작업 환경 제한 / 위험: 사용자 창 배치 방해.
- **대안 B, 선택:** 보조 패널 접기·복원과 인라인 전환 안내 — 장점: 문서 공간 확보 / 단점: 상태·포커스 관리 필요 / 위험: 접힌 작업·진행 상태 발견성 저하.
- **완료 조건:** 1440×900·1280×800·800×600에서 주요 행동 접근이 가능하고, 패널 접기·보기 변경 시 선택·스크롤·코멘트 앵커를 유지한다. 150%·200% 확대를 별도로 확인한다.
- **Impeccable 후속:** `adapt`, `layout`.

### UX-05 · P2 · AI 연결 설정이 상태보다 버튼 목록을 앞세운다

- **확인 사실:** [ConnectionSettings.tsx](apps/desktop/src/connection/ConnectionSettings.tsx)는 재확인·경로 변경·로그인·테스트를 나열하며 테스트만 READY 상태에 따라 제한한다. [연결 캡처](docs/usage/images/ai-connection.png)에서 행동들의 시각적 무게가 비슷하다.
- **영향 가설:** 설치·로그인·연결 준비·테스트 성공 상태마다 사용자가 다음 행동을 해석해야 한다.
- **대안 A:** 단계형 위저드 — 장점: 순서 명확 / 단점: 재진단 시 왕복 / 위험: 이미 준비된 사용자의 반복 비용.
- **대안 B, 선택:** 현재 확인창에서 상태별 권장 행동 강조 — 장점: 변경 작음 / 단점: 상태별 문구 설계 필요 / 위험: 원인이 불명확한 실패를 잘못 분류할 수 있음.
- **완료 조건:** 미설치·로그인 필요·준비·성공·실패 각각에 다음 행동이 보인다. 기술 정보는 상세로 제공하고, 로컬 편집에는 연결이 필요 없다는 안내와 수동 재확인을 유지한다.
- **Impeccable 후속:** `onboard`, `clarify`.

### 추가 개선 후보

- **P2:** 코멘트 저장 완료 시 “아직 AI에 전달하지 않았습니다”와 재제안 진입점을 연결한다. 코멘트 저장이 자동 AI 실행으로 바뀌어서는 안 된다. [CommentForm](apps/desktop/src/review/CommentForm.tsx), [RegenerateForm](apps/desktop/src/review/RegenerateForm.tsx) 근거.
- **P2:** 요청이 비활성인 경우 해당 위치에 이유와 가능한 다음 행동을 제공한다. 전역 생성 상태·저장 오류를 중복 경보 없이 연결한다.
- **P3:** `rN`, `N개 블록` 등 내부 단위는 보조 정보로 낮추고 사용자가 판단할 섹션·인용·행동을 앞세운다.
- **P3:** 승인·요청은 주요 행동으로, 수동 저장·복구 등은 상황에 맞는 보조 행동으로 표현한다. 기존 색·포커스·오류 상태와 일관되게 적용한다.

## 7. 결정과 가정 ADR

### ADR-UX-001 · 기존 작업 화면에서 점진적으로 개선

- **상태:** 분석 문서의 제안. 제품 구현·승인된 신규 요구사항은 아님.
- **가정:** PRD의 단일 Markdown 작성자가 주 사용자이며, 반복 요청·부분 검토가 주요 이용 형태다. 실제 빈도·숙련도 분포·이탈률은 확보하지 못했다.
- **선택:** 기존 문서 중심 3열 구조를 유지하고 요청·범위·결정의 위치와 위계를 먼저 개선한다.
- **대안:** 단계별 화면으로 전면 분리하면 초보자 안내는 쉽지만 비교·재요청 사이 이동과 상태 전달 비용이 증가한다. 조건을 항상 펼치면 발견성은 좋지만 반복 작업 공간을 계속 차지한다.
- **장점·단점·위험:** 작은 변경으로 검증할 수 있음 / 일부 추가 공개 동작 필요 / 접힌 조건·패널의 상태를 놓치지 않도록 요약·포커스·저장 상태 검증 필요.
- **재검토 조건:** 사용성 검증에서 사용자 다수가 작업·확정본·제안의 개념을 계속 구분하지 못하거나 단순 배치 개선으로 첫 요청 성공이 개선되지 않을 때.

### 변경 영향도

이번 변경은 비어 있던 루트 SPEC.md에 분석을 작성하는 문서 변경이다. 기존 기능 명세·FR/INV/AT 번호·소스·테스트는 변경하지 않는다. 저장소 문서에서 루트 SPEC.md로 향하는 참조는 검색 결과 없었으며, 기존 `docs/product/specification.md`를 대체하지 않는다.

아래는 구현 시 수행할 순서이며 이번에 완료한 구현 목록이 아니다. 각 단계는 해당 정의·참조·호출·테스트·설정 파일을 전체 읽고, 변경할 심볼을 전역 검색한 뒤 별도 변경으로 진행한다.

## 9. 검증과 완료 기준

### 9.1 자동·수동 검증 계획

새 동작에는 새 테스트를, 동작 결함을 수정할 때는 먼저 실패하는 회귀 테스트를 추가한다. 테스트는 합성 문서·가짜 CLI·임시 DB로 독립 실행하며 사용자 계정과 실제 사용 한도를 사용하지 않는다.

| 영역 | 성공 경로 | 실패·경계 경로 |
| --- | --- | --- |
| 요청·조건 | 기존 작업에서 조건 수정 후 선택 범위 요청, 최신 조건 전달 | 조건 저장 실패 시 요청 금지·입력 보존. 빈 선택은 전체로 확대 금지 |
| 검토 | 선택 그룹 승인 후 다음 그룹과 대상 일치, 나란히 전환 후 유지 | 외부 수정·기준 변경·중복 클릭 시 잘못된 적용 0건, 결합 그룹 부분 적용 금지 |
| 생성·코멘트 | 코멘트 저장 후 명시적 재제안, 새 후보는 미승인 | 재제안 실패·중단 시 기존 후보·코멘트 유지, 늦은 응답 미적용 |
| 배치·접근성 | 각 창 크기·확대·키보드로 요청·승인·복원까지 도달 | 긴 제목·조건·변경 100개·패널 접힘·오류 배너에서 가림과 포커스 유실 확인 |
| 연결·내보내기 | 상태별 권장 행동, 저장된 확정본 복사 | 로그인 실패에도 로컬 편집 가능, 미승인 제안 내보내기 제외 |

기존 `generation.e2e.mjs`, `navigation.e2e.mjs`, `layout.e2e.mjs`에는 조건 전달·실패 보존·작업 선택·긴 줄·150% 확대 검사 소스가 있다. 이를 활용하며 “검사가 전혀 없다”고 판단하지 않는다. 이 검토에서 해당 테스트를 실행한 것은 아니다.

UI 변경 후 `apps/desktop`에서 `npm run typecheck`, `npm run lint`, `npm run test:unit`, `npm run build`를 실행한다. 네이티브 E2E 빌드 완료 후 변경 영역의 generation/review/layout/navigation/connection 시나리오와 성공·실패 경로를 실행한다. 빌드와 E2E를 병행하지 않고 검사 후 일반 앱 빌드를 복원한다. 도메인·IPC 변경이 필요해지면 별도 범위로 계약·Rust 검사를 추가한다.

VoiceOver·실제 한국어 IME·OS 파일 선택 및 저장 대화상자는 일반 앱에서 수동 확인한다. 버튼·본문·상태의 대비, 포커스 가시성, 200% 확대는 렌더링 결과로 확인한다. 전송 확인·버전 검증·operation ID 기반 중복 방지·앱 전체 생성 한 건 제한을 UI 편의 때문에 우회하지 않는다. 문서·요청·인증 원문을 로그에 남기지 않는다.

### 9.2 사용자 검증과 측정

초보·반복 사용자 관점으로 최소 5명의 형성 평가를 제안한다. 이는 통계적 대표성 검증이 아니다. 개선 전후에 동일한 합성 여행 안내 문서를 사용하고, 10분→5분의 의도하지 않은 수치 변경을 발견하여 거절하는 과제를 포함한다.

| 지표 | 측정 방법 | 제안 목표·해석 |
| --- | --- | --- |
| 첫 요청 성공 | 외부 설명 없이 수정 요청 시작, AI 대기 시간 제외 | 5명 중 4명 이상. 현재 기준값은 미측정 |
| 범위 이해 | 실행 전에 대상 부분을 말하고 실제 요청 원문과 대조 | 5명 모두 범위 오인 없이 설명. 적은 표본의 탐색 목표 |
| 오승인 예방 | 수치 변경을 발견하고 거절하는지 관찰 | 5명 모두 잘못된 수치 미반영 |
| 반복 효율 | 요청 3회·변경 10개 검토의 조작·스크롤·UI 시간 비교 | 기준값부터 수집하고 감소 여부 확인. 검토를 생략해 빨라진 결과는 제외 |
| 복구 이해 | 제안 취소와 버전 복원의 차이 설명·실행 | 기존 확정본·후보의 보존 범위를 이해하는지 확인 |

지표는 테스트 관찰로 수집하고 자동 텔레메트리를 추가하지 않는다. 현재 이탈률·오류율·처리 시간이나 개선 효과의 수치는 주장하지 않는다.

## 10. 문서 적용 범위

이 문서는 개선 검토의 기준이며 현재 기능을 구현했다고 선언하지 않는다. 우선 UX-01~03을 작은 변경으로 검증하고 UX-04~05를 이어 진행한다. UI 배치 변경 중에도 기존 기능 명세의 불변 규칙과 인수 기준을 유지한다. 실제 사용자 결과가 가설과 다르면 우선순위와 ADR을 갱신한다.
