# 선택 수정 대상 확장 결정

상태: 저장·실행·UI 구현 반영, 최종 native 화면 검증 대기 · 관련 작업: SPEC T14/T15 · 2026-11-01

## 배경과 제약

기존 후보 일부 수정은 같은 제안의 새 revision이다. 변경 없는 문맥·이미 승인된 본문은 현재 확정본의 새 제안이며, 전체 재작성 후보 일부 수정은 새 전체 후보다. 세 결과의 승인 단위와 기준 좌표를 구분한다. 확정본은 승인 전까지 유지하며 기존 미승인 제안을 자동 보관 처리하지 않는다.

## T14 대안

| 대안 | 장점 | 단점·위험 |
| --- | --- | --- |
| 현재 head 선택을 기존 batch base로 역매핑해 같은 묶음에 추가 | 활성 묶음 한 개 유지 | 승인으로 새로 생긴 문구에는 원래 base의 대응 구간이 없다. 예: `준비`를 승인하여 `확인이 끝난 준비`가 된 뒤 `끝난`을 선택하면 원래 위치가 유일하게 결정되지 않는다. |
| 현재 head 기준의 별도 묶음을 만들고 기존 활성 묶음을 유지 | 기존 좌표·결정·코멘트를 다시 쓰지 않고 정확한 현재 원문 검증 가능 | 같은 작업의 여러 활성 묶음 탐색과 승인 시 다른 묶음에 미치는 영향을 안내해야 한다. |

두 번째 안을 선택한다. 모호한 역매핑은 금지한다. 새 부분 제안 생성만으로 기존 묶음을 ARCHIVED로 바꾸지 않는다. 전체 생성 요청의 기존 보관 정책은 유지한다.

현재 확정본에서 유효한 미승인 PATCH 구간과 겹치는 선택은 새 제안으로 중복 등록하지 않고 해당 후보 수정으로 안내한다. 다른 묶음의 승인으로 head가 바뀌면 기존 STALE 규칙은 그대로 적용한다. 보존은 승인까지 유효성을 무조건 유지한다는 의미가 아니다.

일반 생성·재작성 확인은 최신 활성 묶음을 기준으로 검사하고, 기존 활성 묶음 전체를 보관 처리하는 영향을 표시한다. 검토 목록에서 활성 묶음 모두를 열 수 있게 한다.

## T15 대안

| 대안 | 장점 | 단점·위험 |
| --- | --- | --- |
| 모델이 전체 재작성 후보를 다시 반환 | 기존 응답 모드 재사용 | 선택 밖 문자열 보존을 보장할 수 없음 |
| PATCH 교체 문자열을 받아 Rust에서 전체 후보에 결합 | 선택 밖 보존을 검증 가능 | 선택 실행 기록과 새 REWRITE 묶음 등록 경계가 필요 |

두 번째 안을 선택한다. 기준 head·후보 ID·후보 해시·정확한 인용을 준비와 저장 직전에 검사한다. 성공 시 원래 후보만 이력으로 옮기고 새 전체 후보를 만든다. 적용은 전체 문서 단위를 유지한다.

## 계약과 영향

두 확장은 기존 RegenerateRequest의 proposal ID 의미를 바꾸는 대신 별도 typed 선택 요청을 사용한다. 로컬 작업·문맥·모델을 저장하고 기존 공급자 실행·단일 생성·중단·세션 완료 처리를 재사용한다. 대화 결과는 새 job에 실제 등록된 batch로 연결한다. 중단·충돌·늦은 응답·원자적 저장 실패에는 새 유효 결과가 없다.

검증: 현재 head에서의 승인 이후 선택, 미승인 구간 겹침, 여러 활성 묶음 보존, 전체 후보 범위 밖 일치, 취소·중복·재시작·잘못된 응답을 결정적 fixture로 검사한다.
