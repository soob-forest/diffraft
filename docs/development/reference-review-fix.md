# 참조 링크 변경 단위 수정

2026-11-04 · 상태: 수정·검증·수정본 설치 완료

## Problem 1-Pager

- 배경: 전체 재작성 후보를 로컬에서 독립적인 승인 단위로 나눈다.
- 문제: `[my label]` 사용처와 `[my   label]:` 정의를 원시 문자열로 비교해 서로 다른 단위로 나눈다. 정의 삭제만 승인하면 정상 링크가 일반 문자열로 깨진다.
- 목표: Markdown 파서가 해석한 실제 참조의 사용처·정의 변경을 함께 결정하고, 이미 저장한 구버전 계획에서도 불안전한 부분 승인을 차단한다.
- 비목표: 후보 본문·원문 바이트 정규화, DB/IPC 변경, 기존 계획·단위 ID·번호·의견 재작성, 이미 확정한 사용자 문서 자동 수정.
- 제약: 파일300행·함수50행·매개변수5개·복잡도10 이내. 합성 문서·임시 DB로 먼저 실패를 확인하며 빌드·Cargo·native 검사를 순차 실행한다.

## ADR-REFERENCE-001: 실제 참조 연결

| 대안 | 장점 | 단점·위험 | 결정 |
| --- | --- | --- | --- |
| 문자열 내부 공백 축약 후 비교 | 작은 수정 | 코드·인라인 링크를 참조로 오인하고 Unicode case folding·여러 줄·이스케이프 규칙을 중복 구현 | 제외 |
| 전체 문서의 파서 reference 정의·Link/Image 이벤트 범위로 연결 | 앱이 사용하는 파서의 동일 라벨 해석과 실제 문법 문맥을 따름 | 원문·후보 각각의 추가 파싱 및 범위 소유자 대응 필요 | 채택 |

가정: 고정된 pulldown-cmark 0.13.5의 resolved reference definition span과 usage event span을 바이트 좌표로 사용한다. BOM은 파싱에서만 제외하고 좌표에 다시 더한다. 공백·Unicode·줄바꿈·원문/후보 문자열 자체는 변경하지 않는다. 원문과 후보 양쪽의 연결을 합쳐 생성·삭제·이름 변경을 모두 보호한다. 새 계획의 algorithmVersion은2로 기록한다.

영향: `rewrite_plan → rewrite_groups → rewrite_references`의 연결만 변경한다. 파서가 참조로 해석하지 않는 코드·일반 텍스트·인라인 링크를 임의 결합하지 않는다. 편집 연산의 범위·본문·순서와 적용 검증은 유지한다.

## ADR-REFERENCE-002: 이미 저장한 v1 계획

| 대안 | 장점 | 단점·위험 | 결정 |
| --- | --- | --- | --- |
| 계획을 다시 분해하거나 v1 전체 승인 잠금 | 단순한 최신화/차단 | ID·의견 연결 손상 또는 무관한 안전 단위와 정상 일괄 승인까지 차단 | 제외 |
| v1 승인 직전에 요청이 닿는 참조 연결 집합 검증 | 기존 ID·회차·의견과 무관한 단위 승인 유지 | 요청별 그래프 계산과 과거 결정 조합 규칙 필요 | 채택 |

가정: 요청이 닿는 참조 연결 집합의 모든 변경은 이미 승인됐거나 이번 요청에 포함돼야 한다. 거절한 관련 단위가 있으면 기존 다시 검토로 복귀한 뒤 함께 승인한다. 구버전에서 이미 일부 승인한 집합의 나머지 수습 승인은 허용한다. 기존 사용자 문서를 자동 되돌리거나 단위를 다시 번호 매기지 않는다.

영향: `accept_proposals`의 최신 head·기존 그룹 검증 뒤, 파일 쓰기 전에만 추가 검사한다. 기존 committed 재실행은 중복 저장 없이 기존 경로로 반환한다. 거절·재검토·코멘트·조회와 PREPARED 저널 복구/commit에는 새 정책을 적용하지 않아 업데이트가 기존 복구를 막지 않게 한다.

## 검증과 배포

- 실패 선행: 공백/탭/줄바꿈·대소문자 라벨, 실제 링크/이미지·collapsed/shortcut, 원문 삭제·후보 추가, BOM, 코드/인라인 링크 오결합 방지.
- 기존 v1: 불안전한 단독 승인 거부와 원문/head/결정 불변, 관련 변경 함께 승인·무관한 변경 독립 승인, 거절/재검토·이미 승인한 관련 변경·저널 복구 보존.
- Rust fmt·clippy·관련/기존 순수·저장 검사를 실행한다. UI·생성 계약은 변경하지 않는다.
- 일반 빌드와 설치용 release의 소스/바이너리·서명·테스트 기능 제외를 확인한 뒤 기존 앱·데이터를 백업하고 두 설치 위치를 갱신한다.


## 실행 결과

- 수정 전 `reference-before.log`: 새 분해 회귀5건 모두 실패. 공백/탭/줄바꿈·Unicode·이미지·BOM의 의존성 누락과 코드 문자열 오결합을 고정했다.
- 수정 전 `reference-legacy-before.log`: 구버전 저장 계획5건 중3건 통과·2건 실패. 불안전한 단독 승인과 거절된 관련 변경을 뺀 일괄 승인이 실제 파일에 적용되는 경로였다.
- 수정 후 `reference-integrated.log`: 기존 분해8·새 참조5·구버전 저장/복구5건, 총18건 통과. 새 참조5건 안에서 라벨·문법 조합을 함께 검사한다.
- `reference-native-fmt.log`, `reference-native-check.log`: 전체 Rust fmt·모든 target의 clippy 경고 오류 검사 통과. 이번 변경11개 Rust 파일은 최대200행이며 새/수정 함수는50행·매개변수5개·복잡도10 이내다.
- `reference-native-test.log`: 49개 suite, 371 passed / 0 failed / 30 ignored. 별도 계정·환경 검사가 필요한 ignored 검사는 실행하지 않았다. 합성 문서·임시 DB만 사용했고 실제 사용자 문서·계정으로 테스트하지 않았다.
- 공통 결정 검증·저장 commit·복구 정책은 변경하지 않았다. 구버전의 파일 교체 후 PREPARED 회복과 동일 committed 작업 ID 재시도의 중복 저장 방지도 통과했다.
- UI와 IPC/DB 스키마는 변경하지 않았다. 이번 검증은 분해·실제 임시 파일/SQLite의 승인 성공·실패·복구 경로이며 새 네이티브 UI/E2E 인수로 표현하지 않는다.

기존 v1 계획의 단위 ID·고정 번호·의견·원래 후보는 보존한다. 이미 저장된 잘못된 부분 결정은 자동 수정하지 않으며, 관련 거절 단위를 다시 검토하고 연결된 변경을 함께 승인하는 경로를 제공한다. 새 계획은 버전2로 기록한다.


## 일반 빌드와 설치 완료

`reference-build-normal.log`와 `reference-build-release.log`의 일반/릴리스 빌드가 모두 성공했다. TypeScript·웹·Rust 빌드를 포함하며, 릴리스의 arm64·ad-hoc 서명·앱 실행 파일1개·테스트 표시0건 검증도 통과했다. 웹 main은 일반510.28kB·릴리스510.29kB로 기존500kB 권고 경고가 남아 있다. 이 수정에서 번들 분할·경고 임계값은 변경하지 않았다.

빌드 ID는 `900ce5db58005207-debug` / `900ce5db58005207-release`, source SHA-256은 `900ce5db5800520784ecca153af2a038677e03fc07bcd700898b232a051b16f7`다. 일반/릴리스 실행 파일과 현재 소스의 일치, E2E·장애 주입/계약 생성 표시9종 제외를 `.artifacts/reference-fix-verification.json`에 기록했다. 릴리스 실행 파일 SHA-256은 `311cf94c3d574cf10ac16be0bf18be4a50cd64c0ebae379b8d301029205c9cf9`다.

앱이 실행되지 않은 상태에서 기존 앱 두 벌과 앱 데이터를 소유자 전용 백업 폴더에 보관한 뒤, 서명·파일이 일치하는 staging 앱을 원자적으로 교체했다. `/Applications/DocReview.app`과 `~/Applications/DocReview.app` 모두 수정본이며 교체 중 앱 데이터의 내용 불변을 확인했다. 이후 `/Applications/DocReview.app`을 실행해 올바른 경로·실행 파일 해시·시작 프로세스 유지를 확인했다. 실제 사용자 문서 편집이나 AI 요청은 수행하지 않았다. 설치 증명은 `.artifacts/reference-install.json`에 있다.
