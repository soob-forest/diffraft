## 확인한 재현과 호출 경로

검토의 합성 4개는 기존 `validate_patch`를 통과한 연산으로 실행했으며 일반 독립 수정 1개 통과, 아래 3개 실패였다. 임시 자료는 `apps/desktop/.artifacts/patch-purpose-review.rs / .log`에 있다. Git에서 제외된 임시 자료만 의존하지 않고 PG-21에서 정식 테스트로 옮긴다.

| ID | 재현 | 수정 전 결과 | 기대 |
| --- | --- | --- | --- |
| F01 | 서로 다른 문단의 `불가능 → 가능`, `안정 → 불안정` | 글자 `불`을 이동으로 보아 1그룹 | 독립 2그룹 |
| F02 | 여는 구분자는 그대로 두고 파일 끝 닫는 구분자 뒤에 `invalid` 추가 | 구조가 같다고 조기 반환해 허용 | 새 미완성 코드블록 오류 |
| F03 | 인용문 안 코드블록의 여는·닫는 backtick fence를 tilde fence로 함께 변경 | `>`가 남은 원문을 검사해 오류 | 짝 변경은 결합, 별도 문구 교정은 분리 |

- 신규 등록·원문 부분 요청: `review_register.rs / selection_results.rs → validate_patch → regroup_patch → patch_groups::plan`.
- 직접 후보·선택 수정·재제안: `revisions.rs / review_history.rs / regeneration_result.rs → persist_revision → regroup_patch`.
- 기존 묶음 준비: `patch-review-read.ts → prepare_patch_review → eligible / validate_source → regroup_patch`.
- 판정: `patch_groups.rs → move_edges / change_core / patch_structure::edges → shape / validate_fence`.
- 결정·복구: `document/review.rs`, `review_decisions.rs / review_effects.rs`가 그룹 전체와 예상 그룹 revision을 검사한다.

영향: 신규·revision·준비의 그룹 구성과 구조 오류 허용 범위가 바뀐다. 화면 계약은 유지하며 기존 그룹 revision으로 보낸 결정은 계속 거부해야 한다. 공유 `parse.rs`나 REWRITE 분석을 바꾸게 되면 해당 호출처·테스트를 전체 읽고 영향도를 먼저 기록한다.

## ADR-003: 이동과 fence 판정 경계

상태: 채택. 구현 전 아래 가정을 회귀로 고정한다.

| 쟁점·대안 | 장점 | 단점 | 위험 |
| --- | --- | --- | --- |
| 이동: 현재 문자열 일치에 최소 길이만 추가 | 수정이 작다. | 긴 단어는 오판하고 짧은 실제 문단은 누락한다. | 길이 임계값이 검토 의미를 결정한다. |
| 이동: 완전한 문단 경계·동일 본문·유일한 출발/도착 확인 | 문단 이동과 단어 교정을 구분한다. | 전후 문단 범위와 연산 문맥을 확인해야 한다. | 문맥 교체·줄바꿈 경계의 누락을 테스트해야 한다. |
| fence: 기호 접두사 비교와 원문의 `>`/공백 일괄 제거 | 구현이 단순하다. | 컨테이너와 코드 본문을 구분하지 못한다. | 잘못된 닫힘 허용·본문 변형·좌표 오염이 가능하다. |
| fence: 파서의 컨테이너·행 범위와 명시적인 구분자/닫힘 상태 사용 | 정상 중첩과 새 구조 오류를 구분한다. | 좁은 범위의 분석 보완이 필요하다. | 원래 오프셋을 유지하는지 확인해야 한다. |

각 쟁점의 두 번째 안을 선택한다. 기존 Markdown 파서를 재사용하고 필요한 순수 분석만 분리한다. 전체 Markdown 파서를 새로 만들지 않는다.

- 이동은 실제 일반 문단 전체의 삭제·추가가 유일하게 대응할 때 결합한다. 한 글자여도 완전한 문단이면 후보가 될 수 있으므로 최소 글자 수를 근거로 삼지 않는다.
- 공통 앞뒤 문맥 제거는 후보 탐색에만 사용한다. 문단 경계 검증 없이 일치한 내부 문자열을 이동의 증거로 쓰지 않는다. 문단 본문은 바이트로 비교하고 문단 사이 분리자는 경계로 식별한다.
- fence의 문자·길이·닫힘 유효성·컨테이너를 구분한다. 닫힘 위치를 바꾼 결과가 뒤따르는 본문·짧은 구분자·다른 문자 때문에 새 미완성 블록이 되면 거부한다. 실제 닫힘이 따로 있는 코드 본문의 유사 구분자는 데이터로 취급하고, 정상 긴 닫힘·허용 공백·언어 정보는 유지한다.
- `shape`가 같더라도 변경이 건드린 fence 경계의 유효성 검사를 생략하지 않는다. 시작 태그만으로 닫힘·중첩 관계가 같다고 가정하지 않는다.
- 인용·목록 접두사는 파서가 식별한 문맥에만 적용한다. 분석용 정보는 원문 바이트 범위와 연결하며 저장 문자열·좌표를 고치지 않는다. 코드 본문의 `>`나 들여쓰기는 데이터다.
- 이번 변경으로 새로 생기는 구조 오류를 차단한다. 무관한 위치에 있던 미완성 코드블록 때문에 일반 문구 교정 전체를 거부하지 않는다.

## ADR-004: 저장된 정책 v1의 적용 범위

| 대안 | 장점 | 단점 | 위험 |
| --- | --- | --- | --- |
| 판정 함수만 수정하고 v1 유지 | 저장 변경이 없다. | 이미 저장된 잘못된 결합은 준비 명령이 건너뛴다. | 기존 사용자에게 F01이 계속 남는다. |
| 정책 v2로 올리고 전부 미처리 묶음만 명시적 준비에서 전환 | 기존 미처리 사례도 고친다. | 준비 조건·이벤트·호환성 검사가 추가된다. | 경합·부분 저장·오래된 결정은 트랜잭션과 revision으로 통제해야 한다. |

두 번째 안을 선택한다. 기존 `policy_version`·`revision` 필드를 사용하므로 새 DB 스키마나 IPC 필드는 추가하지 않는 것을 기본으로 한다. 필요가 생기면 변경 전 ADR에 근거를 기록한다.

- 새 등록·명시적 후보 revision은 정책 v2를 사용한다. 자동 전환은 메타데이터 없음 또는 v1인 `ACTIVE PATCH`이고 모든 최신 제안이 `PENDING / VALID`인 현재 head에만 적용한다.
- v2는 반복 준비해도 바꾸지 않는다. 미래 정책을 낮추지 않는다. 일부 승인·거절/취소된 묶음·이전 기록·REWRITE는 자동 전환하지 않는다.
- 문서 락 아래 head·파일·생성 상태를 재검증하고 그룹·이유·정책·revision·전환 이벤트를 함께 저장한다. v1의 그룹 revision은 증가시키며 1로 초기화하지 않는다.
- 구성원이 같은 그룹 ID는 유지한다. 기존 proposal ID/revision·코멘트·결정·원문은 유지한다. 이벤트에는 전후 정책 버전과 그룹 식별자를 남기고 본문·비밀값은 넣지 않는다.
- 새 판정이 저장된 잘못된 fence를 거부하면 정책이나 일부 그룹만 먼저 갱신하지 않는다. 명확한 오류를 표시하고 기존 데이터를 보존한 채 원문/새 요청으로 복귀할 수 있어야 한다.
- 결정·승인 저널은 기존 예상 그룹 revision 검증과 멱등 재생을 유지한다. 과거의 이미 승인된 내용을 새 규칙으로 다시 교정하거나 재생 거부하지 않는다.

## 실행 순서와 완료 증거

PG-21 실패 재현 → PG-22 이동 판정 → PG-23/24 구조 판정 → PG-25 정책 전환 → PG-26 저장 통합 → PG-27 화면 → PG-28 최종 회귀 순서로 진행한다. 파일 수정 전 전체 파일과 참조·호출·테스트·설정을 읽는다. 기존 테스트 파일이 300 LOC를 넘으면 새 파일로 나눈다.

`apps/desktop`에서 아래 명령을 순서대로 실행한다. 정식 회귀를 등록한 직후에는 해당 테스트만 먼저 실행해 실패를 확인한다. 계약 변경 시 Rust에서 생성한 뒤 검사하고 생성물을 직접 수정하지 않는다.

```sh
npm run typecheck
npm run lint
npm run test:unit
npm run native:fmt
npm run native:check
npm run native:test
npm run contracts:check
npm run build
npm run native:build:e2e
npm run test:e2e -- review
npm run test:e2e -- regeneration
npm run test:e2e -- selection-transitions
npm run test:e2e -- rewrite-review
npm run test:e2e -- history
npm run test:e2e -- recovery
npm run test:e2e -- usability
npm run native:build
```

Cargo·빌드·네이티브 E2E는 병렬 실행하지 않는다. 새 실패·변경·미해결 위험이 없으면 통과한 검사를 반복하지 않는다. 합성 문서·고정 응답·소유한 임시 DB로 성공/실패/재시작을 검사한다.

완료 시 새 보완 실행 기록에 F01~03·FA01~08 및 기존 AC의 실제 결과, 선행 실패/수정 후 통과, UTC 또는 UTC offset이 있는 실행 시각, 소스/바이너리 해시, 오류·경고·수동 미확인을 남긴다. 기존 48개 E2E와 1차 완료 체크는 보완 완료 증거로 재사용하지 않는다. 이번 계획 작성 단계에서는 제품 코드·스키마·설치 앱·사용자 DB를 변경하지 않는다.

## 열린 질문

차단 질문 없음. 지원 Markdown 문법은 현재 파서와 기존 계약을 따른다. 의미상의 이동 추론이나 일부 처리 묶음의 자동 복구가 필요해지면 별도 작업으로 계획한다.

현재 실행 결과: [보완 구현·검증 기록](patch-groups-followup-implementation.md). 잠금 해제 후 새 빌드의 네이티브 E2E 50개를 통과했고 PG-21~28을 완료했다.
