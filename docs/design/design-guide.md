# 화면 및 디자인 시스템 명세

버전 0.3 보완안 · 2026-10-29 기준 정정 · 원본 자산: [assets](assets)

**현재 6개 화면의 최종 시각 기준은 [usability-comparison.html의 오른쪽 TO-BE](usability-comparison.html)다.** [현재 TO-BE 계약](#13-현재-to-be-계약)과 [실행 기록](../development/tobe-implementation.md)를 따른다. 아래1~6절/S00~S10과7~11절 분석은 이력·보조 근거이며 TO-BE와 충돌하는 수치·배치는 현재 계약이 아니다. 원본 SVG·PNG와 과거 Impeccable 평가는 보존한다.

## 1 디자인 방향

문서를 작성하는 동안은 편집기, AI 변경을 검토하는 동안은 diff 도구처럼 동작한다. 확정본·미승인 제안·작업 대화의 경계를 화면에서 드러낸다. 승인 행동은 그 행동이 적용할 변경 가까이에 두고 전체 승인은 상단의 현재 제안 묶음 도구 영역에 둔다.

| 참고 제품 | 확인한 동작 | 이번 설계에 채택 | 채택하지 않는 범위 |
| --- | --- | --- | --- |
| VS Code | 인라인/나란히 diff, 변경 간 이동, 변경 구간 조작 | 소스 diff, 좌우 비교, 문맥 접기, 구간별 행동 | Git staging·commit 작업 흐름 |
| GitHub 리뷰 | diff 보기 전환, 줄/범위 코멘트, 제안 검토 | before/after 구간 코멘트, 검토 진척 | PR·다중 검토자·병합 승인 |
| Google Docs | 원문을 유지하는 제안, 개별/전체 승인, 제안 코멘트 | 미승인 제안 분리, 남은 변경 전체 승인 | 공동 편집·알림·계정 권한 모델 |
| Obsidian | Markdown 원문 편집과 읽기 화면 | 편집/미리보기 구분, 문서 중심 탐색 | 플러그인 생태계·지식 그래프 |
제품 사실은 [공식 참고 자료](../references.md)에 근거한다. 채택 여부와 화면 수치는 이 앱에 대한 설계 판단이다. 공식 화면의 픽셀·아이콘·브랜딩을 복제하지 않았으며 모든 전달 화면은 이 제품을 위해 새로 작성했다.

## 2 기본 화면 구조

시안 캔버스는 1600×1000이다. PNG는 3200×2000이며 SVG는 같은 논리 좌표를 사용한다.

| 영역 | 크기 기준 | 역할 |
| --- | --- | --- |
| 앱 상단 | 높이 50 | 제품명, 작업 공간 |
| 왼쪽 탐색 | 폭 220 | 문서, 문서별 작업, 목차 또는 변경 목록, 연결 설정 |
| 문서 헤더 | 높이 74 | 문서명, 확정본 버전, 실제 저장 상태, 버전 기록, 내보내기 |
| 모드 탭 | 높이 52 | 편집 / 변경 검토 / 미리보기 |
| 검토 도구 | 높이 약 52 | 비교 기준, 보기 모드, 문맥 접기, 이동, 전체 승인 |
| 중앙 본문 | 유동 폭 | 소스 편집기 또는 실제 diff |
| 오른쪽 작업 패널 | 기본 폭 360, 접기 가능 | 작업 대화, 고정 조건, 코멘트, 맥락 |
| 하단 상태 | 높이 32 | 로컬 작업, 인코딩, 승인 상태 원칙 |
실제 창 크기와 OS 배율은 구현에서 검증한다. 최소 창 목표는 1280×800이며, 폭이 부족하면 왼쪽 탐색과 오른쪽 대화를 접을 수 있다. 나란히 보기의 각 열 폭이 540 미만이면 인라인 전환을 권장한다. 사용자가 고른 보기 설정을 임의로 바꾸기보다 전환 행동과 이유를 보여준다. 창 축소로 인라인이 필요한 경우 선택 변경과 코멘트 앵커를 보존한다.

## 3 Diff 컴포넌트

### 3.1 표현 규칙

- 인라인: `이전 행 번호 / 이후 행 번호 / − 또는 + / 원문` 순서다. 삭제 줄은 이전 번호만, 추가 줄은 이후 번호만 가진다.
- 나란히: 왼쪽 확정본, 오른쪽 제안 반영 예상본. 각 열의 행 번호는 그 문서를 기준으로 한다.
- 줄 배경은 변경의 종류를, 진한 부분 배경은 바뀐 표현을 나타낸다. 색만으로 상태를 전달하지 않는다.
- 변하지 않은 문맥은 중립색으로 표시한다. 줄 번호 차이가 큰 구간은 문맥 더 보기로 펼칠 수 있다.
- 추가/삭제 통계는 실제 줄 차이이고 승인 개수는 독립 승인 그룹 수다.
- 긴 줄은 기본 자동 줄바꿈한다. 코드·표를 읽기 위해 가로 스크롤을 선택할 수 있으나 원문을 잘라 저장하지 않는다.
- diff 화면에서 직접 확정본을 편집하지 않는다. 후보를 수정하려면 `제안 직접 수정`, 원문을 수정하려면 `편집` 탭을 선택한다.

### 3.2 행동과 상태

| 컴포넌트 | 기본 행동 | 실행 이후 |
| --- | --- | --- |
| 변경 헤더의 승인 | 해당 그룹의 현재 revision만 적용 | 승인됨, 새 확정본 버전 표시 |
| 변경 헤더의 거절 | 해당 그룹을 반영하지 않음 | 처리됨 목록으로 이동, 원문 유지 |
| 코멘트 | 현재 변경 또는 선택한 before/after 구간에 연결 | 오른쪽 코멘트 패널 표시 |
| 제안 직접 수정 | 별도 후보 편집 상태 열기 | 저장한 새 revision은 다시 미승인 |
| 남은 변경 N개 승인 | 현재 문서·현재 묶음의 대상 확인창 | 최종 승인 시 유효성 전체 검사 후 저장 |
| 변경 부분만 | 변하지 않은 구간 접기 | 내용·결정 상태 불변 |
| 이전/다음 변경 | 다음 독립 승인 그룹으로 이동 | 선택·포커스·대상 코멘트 함께 갱신 |
| 전체 재작성 적용 | 후보 전체를 적용 | 적용 전 버전 보관, 새 확정본 생성 |

### 3.3 특수 상태

승인·거절·교체·취소는 처리된 기록이고, 기준 불일치·충돌은 현재 제안의 유효성 문제다. 둘을 같은 상태 색 하나로 합치지 않는다. 승인이 불가능하면 이유를 버튼 가까이에 표시하고 최신 문서에서 재제안하는 행동을 제공한다.

재작성 모드는 실제 diff를 보여주되 구간별 승인 버튼을 없앤다. 전체 승인과 전체 재작성 적용의 레이블을 구분한다. 버전 복원은 현재→선택 버전의 방향으로 diff를 보여주며 기존 버전을 덮는 대신 새 버전을 만든다고 명시한다.

## 4 글꼴·색·간격

정확한 값은 [design-tokens.json](assets/design-tokens.json)에 있다. PNG는 NanumGothic으로 렌더링했다. SVG는 글자와 도형을 편집할 수 있으며 글꼴 미설치 환경에서는 대체 글꼴에 따라 줄 폭이 달라질 수 있다. 전달된 PNG를 외형 기준으로 삼는다.

| 역할 | 값 | 사용처 |
| --- | --- | --- |
| 기본 본문 | #182537 | 제목과 본문 |
| 보조 문구 | #607083 | 설명, 상태, 행 번호 |
| 주요 행동 | #2957C8 | 승인·전송·선택 탭 |
| 추가 줄/표현 | #E8F5EC / #B6E1C2 | + 추가 |
| 삭제 줄/표현 | #FDEDEC / #F6C1BB | − 삭제 |
| 추가/삭제 글자 | #14633B / #A0332D | 색과 기호를 병행 |
| 경고 | #FFF3D9 / #815A13 | 충돌, 재연결 |
| 기본 간격 | 4, 8, 12, 16, 24, 32 | 컴포넌트 내부·영역 간격 |
| 둥근 모서리 | 6, 8, 12 | 버튼, 패널, 확인창 |

본문 16~18px, 제목 22~30px, 보조 문구 12~14px를 기준으로 한다. 실제 제품은 글꼴 크기 조절과 OS 배율을 따른다. 색 대비는 기본 본문과 주요 행동에서 WCAG AA 수준을 목표로 검증하며 이 시안 자체가 인증을 의미하지 않는다.

## 5 키보드와 접근성

- 모든 승인·거절·코멘트 행동을 Tab으로 접근할 수 있게 한다. 아이콘만 있는 이동 버튼에 접근성 이름을 제공한다.
- F7/Shift+F7을 다음/이전 변경의 후보 단축키로 제안한다. 실제 충돌 여부를 OS에서 검증한다.
- Ctrl/Cmd+Z는 직접 편집 구간만 되돌린다. 승인과 버전 복원을 같은 단축키로 숨기지 않는다.
- 전체 승인 단축키는 MVP에서 두지 않는다. 승인 단축키 오입력으로 큰 범위가 반영되는 일을 줄인다.
- 확인창은 제목·대상·버튼을 스크린리더가 읽고, Esc로 닫으면 원래 버튼으로 포커스를 돌린다. Enter는 현재 포커스가 놓인 버튼만 실행한다.
- diff의 읽기 순서는 변경 제목 → 삭제 → 추가 → 문맥 → 행동이다. `추가`, `삭제`, `미승인`, `충돌`을 음성으로도 구분한다.
- 재생성 후 새 제안 도착, 승인 완료와 오류는 과도한 포커스 이동 없이 상태 영역으로 알린다.

## 6 화면 자산 목록과 사용법

원본 S00~S10의 화면 이름과 미리보기는 [화면 갤러리](gallery.html)에서 확인한다.

각 이름에 `.svg`와 `.png`가 있으며 `assets/screens/`에 별도로 보관한다. [화면 갤러리](gallery.html)는 PNG를 내장하므로 HTML 하나로도 열 수 있다. 갤러리의 시나리오 선택과 확대만 작동하며 화면 안 제품 버튼은 정적 디자인이다. 실제 앱 코드를 전달한 것이 아니다.

예외 상태는 [기능 명세](../product/specification.md)와 [시나리오](scenarios.md)의 배너·행동 표로 정의한다. 정적 화면 11개는 모든 반응형·오류 상태의 픽셀 시안을 포함하지 않는다.

## 7 기존 설계와 현재 구현의 차이

기존 [11개 화면 갤러리](gallery.html)는 역사적 설계다. [실제 앱 캡처](../usage/images/README.md)는 구현 결과이며, [6개 전후 비교](usability-comparison.html)의 오른쪽 TO-BE가 해당 화면의 최종 시각 기준이다. 이전 ‘보조 목업’ 분류를 정정한다. 세 자료는 서로 다른 버전이다.

당시 주요 차이는 조건 폼에 밀린 요청·중앙 하단 범위, 330px diff 아래의 승인·코멘트, 작은 창의 패널 구조 미정, 연결 행동의 동일 위계였다. 복원·재개는 기존 기능의 발견성을 보완하는 범위였다. 현재 결함 목록이 아닌 이전 분석이며 [사용성 실행 기록](../development/usability-implementation.md)과 [재구현 기록](../development/design-reimplementation.md)에 호출 경로·변경 근거·검증을 보존한다.

## 8 Impeccable 적용 방식과 설계 판단

모드는 **Operate**다. 사용자는 문서를 읽고 수정 요청을 작성한 뒤 변경을 판단한다. 주요 경로를 `범위·지시 확인 → 요청 → 실제 diff 읽기 → 선택 결정 → 남은 검토`로 고정한다. 읽는 본문과 결정 행동을 가깝게 두고, 목표·조건·기술 진단은 필요할 때 펼친다.

| 적용 기준 | 이 제품에 적용한 판단 | 상세안 |
| --- | --- | --- |
| `distill` | 기능을 없애지 않고 조건·진단의 상시 노출을 줄임 | U01, U06 |
| `layout` | 선택 대상·행동·인용을 근접 배치하고 본문 높이를 확보 | U02, U03, U05 |
| `clarify` | 저장·확인·전송·승인의 결과를 구별하는 문구 | U01~U06 |
| `harden` | 입력 보존, 기준 변경, 실패, 긴 콘텐츠의 복구 경로 명시 | U01~U05 |
| `operate` | 기존 중립색·청색·시스템 글꼴·일관된 조작 유지 | 공통 시각 규칙 |

이 문서는 위 플레이북을 적용한 설계 분석이다. 각 하위 명령으로 제품 수정·실사용 검증을 완료했다는 뜻은 아니다. 기존 critique의 25/40을 새 평가로 재사용하지 않는다. VoiceOver 점검은 제외한다.

| 승인 배치 | S02의 모든 헤더에 주요 승인: 대상 근접 / 긴 그룹에서 사라지고 버튼 경쟁 | 선택 그룹 도구 고정: 긴 diff에도 접근 / 화면에 보이는 그룹과 대상 혼동 | B. 대상명·선택 강조·선택 위치 이동을 함께 제공 |
| 작은 창 | 3열 축소: 동시 노출 / 본문·입력 가독성 악화 | 목록 접기+한 보조 패널: 읽기 공간 확보 / 전환 증가 | B. 현재 작업과 열린 패널을 헤더에 표시 |

가정: 반복 요청과 긴 변경 검토가 주요 과업이며, 800×600에서도 핵심 행동에 접근해야 한다. 실제 빈도는 미측정이다. 540px 열 폭은 기존 설계의 출발값이지 확정 임계값이 아니다. `T6-03`에서 실제 글꼴·배율·열 너비를 측정해 확정한다. 새 전면 테마·패널 드래그 리사이즈·초안 영속 저장은 도입하지 않는다.

동시 차단 원인을 모두 같은 무게로 나열하면 정보를 보존하지만 다음 행동이 흐려진다. U01은 복구·입력 보호 순으로 첫 해결 행동을 안내하고 다른 차단도 유지하는 안을 선택한다. 원인 순서와 작은 창의 한 보조 패널 정책은 검증 전 설계 가정이며 과업 관찰에서 조정한다.

### 공통 시각 규칙

- 원문·diff가 가장 큰 읽기 영역이다. 문서 헤더 → 작업/검토 도구 → 본문 → 보조 맥락 순서를 유지하고, 버튼 행을 위해 별도 큰 카드를 쌓지 않는다.
- 기존 4/8/12/16/24/32 간격을 사용한다. 라벨-입력은 8, 같은 행동 묶음은 8~12, 다른 과업 사이에는 24를 시작값으로 적용한다. 확대·줄바꿈 시 고정 높이로 자르지 않는다.
- 요청에서는 ‘요청 내용 확인’, 검토에서는 ‘선택 변경 승인’을 주요 행동으로 둔다. 전체 승인은 보조 스타일과 명시적 개수로 구분한다. 거절은 오류색 채움 버튼으로 과장하지 않는다.
- 선택 탭은 상태 표시로, 주요 버튼은 실행 행동으로 구별한다. 기존 추가/삭제 배경과 −/+를 유지하고, 조건 위반을 자동 탐지한 것처럼 경고색을 새로 붙이지 않는다.
- 기본 글꼴과 크기 체계를 재사용한다. 시안 PNG의 NanumGothic을 근거로 현재 앱의 플랫폼 글꼴을 일괄 교체하지 않는다. 본문을 작게 줄여 공간 문제를 해결하지 않는다.
- 오류는 해당 행동 옆에 원인·보존된 내용·다음 행동을 표시한다. 장문의 진단은 펼침 영역에 둔다. 완료 알림이 본문을 밀거나 키보드 포커스를 갑자기 빼앗지 않게 한다.

## 9 화면별 상세 개선안

### U01 · 요청과 범위 — S01 · P1 · T1-06, T2-01~05, T3-01~06

**배치:** 오른쪽 작업 패널을 `작업명 → 목표·조건 요약/편집 → 범위·요청 종류 → 요청 내용 → 초안 상태 → 요청 내용 확인 → 작업 대화` 순서로 구성한다. 조건 편집 폼은 기본 접힘이다. 선택 영역 바로 옆 단축 행동을 남긴다면 같은 요청 폼을 열며 전송을 우회하지 않는다.

| 상태·계기 | 화면·행동 | 결과·보존 규칙 |
| --- | --- | --- |
| 작업 없음 | ‘요청과 변경 기록을 묶을 작업을 만드세요.’ + ‘새 작업’ | 생성 후 요청 입력에 포커스. 조건 입력을 필수처럼 표시하지 않음 |
| 조건 접힘 | 목표 요약, ‘고정 조건 2개 · 저장됨’, ‘조건 편집’ | 요약은 원문 조건을 임의 재해석하지 않음. 펼친 상태의 입력도 보존 |
| 조건 수정 중/실패 | ‘조건 저장 중’ / ‘조건을 저장하지 못했습니다.’ + ‘다시 저장’ | 접어도 상태 유지. 저장 실패 시 요청 확인·작업 이동 차단 |
| 범위 유효 | ‘선택 영역 4–5행 · v12’ 또는 현재 섹션 제목, ‘범위 변경’ | 요청 폼으로 포커스를 옮겨도 선택 유지. 저장 후 최신 범위를 재산출 |
| 범위 없음/무효 | ‘선택한 범위를 다시 지정하세요.’ + ‘원문에서 선택’ | 전체 문서로 자동 확대하지 않음. 요청 본문은 그대로 보존 |
| 미전송 입력 | ‘미전송 초안 · 앱을 닫으면 사라집니다.’ | 세션 내 보존만 약속. 상단 ‘원문 저장됨’과 분리 |
| 확인/전송 | ‘요청 내용 확인’ → 기존 확인창의 원문·범위·사용량 안내 → ‘확인 후 요청’ | 첫 버튼은 전송 아님. 확인창 취소·기준 변경 시 작성 폼과 입력 복구 |

**완료 조건:** 긴 조건을 펼치지 않고 현재 대상·지시·다음 행동을 찾는다. 조건·범위를 바꾼 뒤 실제 전달 원문을 대조한다. 저장 실패·IME 조합·확인창 취소에서 중복 요청이나 입력 손실이 없어야 한다.

차단 이유가 동시에 있으면 복구/외부 충돌 → 원문·조건 저장 실패 → 진행 중인 생성 → 데이터·연결 준비 → 범위/입력 순으로 첫 해결 행동을 안내한다. 모든 차단 조건은 계속 적용하며 하나를 해결했다고 다른 조건을 우회하지 않는다. 진행 중인 요청이 다른 작업에 있으면 해당 작업명과 이동 행동을 제공하고 현재 초안을 유지한다. 해결된 메시지는 실제 상태 갱신 후 제거한다. 우선순위는 복구와 입력 보호를 먼저 한다는 설계 가정이며 `T7-02`에서 조합 상태를 검증한다.

### U02 · 읽는 변경과 승인 대상 — S02/S03/S05 · P1 · T4-01~06

**배치:** 묶음 정보와 ‘남은 변경 N개 승인’은 상위 도구 영역, `선택 k/N · 섹션명 → 이전/다음 → 거절 → 선택 변경 승인`은 diff 가까운 고정 도구 영역으로 분리한다. diff는 남은 높이를 사용한다. 오른쪽에는 ‘변경 상세 / 작업·대화’를 두어 작업 조건에 계속 접근할 수 있게 한다.

- 스크롤만으로 승인 대상을 바꾸지 않는다. 선택 그룹이 화면 밖이면 ‘선택한 변경으로 이동’을 표시하고, 도구 영역의 대상명을 유지한다. 그룹 클릭·F7·이전/다음만 선택과 코멘트 맥락을 함께 갱신한다.
- 승인 처리 중 대상 그룹과 실행 버튼을 잠근다. 성공 후 다음 유효 그룹의 제목으로 포커스를 이동한다. 연속 Enter로 새 그룹까지 승인되지 않게 한다. 마지막 처리 후 ‘남은 미승인 변경이 없습니다.’와 ‘확정본 보기’를 제공한다.
- 기준 변경 시 ‘문서가 바뀌어 이 제안을 승인할 수 없습니다.’와 ‘최신 문서에서 다시 제안’을 표시한다. 다시 제안은 기존 확인·실행 경로로 연결하며 자동 실행하지 않는다.
- 전체 승인 확인창은 문서·묶음·포함/제외 그룹을 표시한다. 결합 그룹에서는 ‘승인 그룹 2개 · 제안 3개’처럼 두 수를 구별한다. 확인 중 대상이 바뀌면 창을 닫고 다시 검토하도록 안내한다.
- 긴 한 그룹에서는 본문만 스크롤하고 선택 도구는 유지한다. 후보 직접 수정과 코멘트는 도달 가능한 보조 영역에 둔다. 단순히 `overflow:hidden`으로 잘라 문제를 숨기지 않는다.

**완료 조건:** 1개·100개 그룹, 한 그룹이 화면보다 긴 경우, 결합 그룹, 승인 실패·중복 클릭에서 도구의 대상명과 실제 적용 대상이 일치한다. 전체 승인과 선택 승인을 사용자에게 각각 설명하게 해 혼동을 확인한다.

### U03 · 코멘트 저장과 재제안 — S04 · P1 · T1-04~07, T4-05, T7-03

**배치:** 오른쪽 변경 상세를 `대상 섹션·제안 버전 → 변경 전/제안 쪽 → 인용 → 코멘트 입력 → 초안 상태 → 코멘트 저장` 순서로 구성한다. 재제안 지시는 저장 결과 바로 다음 단계로 연결하며 같은 입력에 두 의미를 부여하지 않는다.

| 상태 | 문구·다음 행동 | 금지할 전이 |
| --- | --- | --- |
| 작성 중 | ‘미저장 코멘트 · 앱을 닫으면 사라집니다.’ | 다른 변경 선택·탭 전환으로 삭제, 다른 대상에 자동 연결 |
| 저장 실패 | ‘코멘트를 저장하지 못했습니다. 입력은 유지됩니다.’ + ‘다시 저장’ | 등록된 것처럼 표시하거나 재제안에 미저장 코멘트 포함 |
| 저장 완료 | ‘코멘트를 저장했습니다. AI에는 아직 다시 요청하지 않았습니다.’ + ‘재제안 지시 작성’ | 저장만으로 AI 호출 |
| 재제안 준비 | 대상 인용과 별도 지시 입력, 전달 범위·사용량 안내, ‘이 변경 다시 제안’ | 빈 지시를 임의 생성하거나 문서 전체로 범위 확대 |
| 재제안 중/실패 | 이전 제안 유지, 진행/실패 원인, 수동 재시도 진입 | 실패한 중간 결과를 새 후보로 표시 |
| 대상 교체 | ‘제안이 바뀌었습니다. 코멘트를 연결할 위치를 확인하세요.’ | 인용이 다르거나 없는데 새 revision에 자동 부착 |

**완료 조건:** 화면·작업 왕복 후 초안의 본문과 대상 쪽·인용이 함께 복원된다. 재제안 성공 후 새 제안은 미승인이고, 기존 코멘트를 자동 해결 처리하지 않는다. 대상 재확인 전에도 작성한 내용은 읽거나 복사할 수 있다.

### U04 · 재개와 실패 후 회복 — S08/S07 · P1 · T5-01~06

- 문서 진입 후 원문 화면에도 ‘검토할 변경 N개 · 작업명’과 ‘검토 이어가기’를 표시한다. 0개이면 불필요한 빈 배너를 만들지 않는다. 기준이 오래된 제안은 유효한 미승인 개수에 섞지 않고 ‘최신 문서에서 재제안 필요’로 표시한다.
- 실패한 대화에는 ‘같은 요청 재실행’과 ‘내용 수정’을 분리한다. 수정은 이전 지시만 초안으로 가져오고 현재 초안이 있으면 ‘현재 초안 유지 / 이전 지시로 바꾸기’를 선택하게 한다. 과거 범위·버전은 자동 재사용하지 않는다.
- 승인 완료는 ‘선택 변경을 v13에 반영했습니다.’와 ‘적용 전과 비교’를 제공한다. 이는 버전 기록 비교 진입이며 즉시 되돌리기가 아니다. 이후 편집도 함께 되돌아갈 수 있음을 diff와 안내로 드러낸다.
- CLI 세션이 없다는 사실은 원인 설명의 보조 정보다. ‘저장된 작업 맥락으로 다음 요청을 이어갑니다.’를 먼저 보여준다. 저장된 검토 복원과 미전송 초안의 재시작 보존을 혼동시키지 않는다.

**완료 조건:** 독립 시나리오 SC07의 v13/D03 r2로 재시작·재개를 확인한다. 주 경로 v15→v14 내용 복원은 새 v16 생성으로 확인한다. 두 분기의 캡처·버전 관계를 혼합하지 않는다.

### U06 · 연결 상태와 권장 행동 — S00 · P2 · T7-01~02, T7-04~05

## 11 미감 검토와 비교 목업 보완

Impeccable `quieter`·`typeset`·`polish` 기준으로 기존 S00~S04/S08, 실제 앱 캡처, 비교 목업을 검토했다. 아래는 전문가의 시각적 판단이며 사용자 선호 조사나 새 휴리스틱 점수가 아니다. 기존 시안은 보존하고 [비교 페이지](usability-comparison.html)의 TO-BE에 적용한다.

**ADR-DESIGN-002:** 새 서체·색·장식으로 인상을 바꾸는 안은 변화가 크지만 기존 제품 정체성과 비교 근거가 약해진다. 기존 남색·청색·시스템 글꼴에서 위계·여백을 정돈하는 안은 변화가 절제되지만 기존 구조를 재사용한다. 후자를 선택한다. 본문16px/1.8과 360px 작업 패널은 검증 전 시작값이며, 미감 개선이 과업 성능 향상을 뜻하지는 않는다.

기준 화면은 ‘기존 디자인 0.2’와 ‘현재 앱’을 선택한다. S04/S08의 작업 상태, S00의 연결 단계, S01의 문서 내용과 최소 창 크기는 새 목업과 다르므로 배치·미감 참고 비교임을 표시한다. 원본 SVG·PNG와 앱 CSS는 변경하지 않는다. 보조 목업의 기능은 정적이며 실패·로딩 시안(T0-06)은 별도로 남는다.

검증: 독립 타이포그래피 평가와 `detect --scope type`를 분리했다. Chrome에서 6개 목업의 본문/패널 표시, 기준 전환·단독·확대·Esc·포커스 복귀, 잘못된 주소 복구를 확인했다. 대표 글자 대비는 5.52~10.19:1, diff는 16px/28.8px이며 680px 비교 페이지는 세로 배치·가로 넘침 없음이다. 정적 목업 검사이며 실제 앱·200% 확대·VoiceOver·사용자 선호 조사는 수행하지 않았다.
