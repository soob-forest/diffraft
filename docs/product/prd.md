# AI 문서 검토 도우미 기획서

문서 식별자 PRD  |  버전 0.2  |  작성 기준일 2026년 10월 26일

> 0.2 개정: 실제 텍스트 diff를 중심으로 화면을 재설계했다. [시나리오별 화면](../design/scenarios.md), [디자인 명세](../design/design-guide.md), [별도 디자인 갤러리](../design/gallery.html)를 함께 읽는다. 화면은 설계 시안이며 실제 제품의 실행 화면이 아니다.


이 문서는 Markdown 문서를 AI와 함께 수정하고, 변경을 검토한 뒤 원하는 부분만 반영하는 설치형 앱의 제품 방향과 MVP 범위를 정의한다. 대상 독자는 기획자, 디자이너, 개발 담당자다. 화면은 설계 시안이며 실제 구현 또는 사용성 검증 결과가 아니다.

## 1 제품 방향과 결정 근거

사용자는 문서 작성 자체보다 AI가 바꾼 내용을 확인하고 통제하는 과정에서 시간을 줄이고자 한다. 앱은 요청부터 제안, 코멘트, 승인, 복원까지 한 작업 안에서 이어 준다. AI 제안은 사용자가 승인하기 전까지 확정본에 반영하지 않는다.

**권장 방향은 로컬 설치형 앱이다.** 별도 앱 서버 없이 문서와 작업 상태를 PC에 보관한다. AI 호출은 사용자가 별도로 설치한 공식 Claude Code CLI를 통해 수행한다. AI 요청에는 네트워크가 필요하다.

| 구분 | 기준 |
| --- | --- |
| 사용자 확정 범위 | Markdown 문서 중심, 변경 비교, 부분 승인, 코멘트를 통한 재수정, 전체 승인, 복원 |
| 사용자 환경 제약 | 사용자가 본인 공식 구독 계정으로 CLI에 로그인하며 앱에 인증값을 입력하지 않음 |
| 최종 문서 사용처 | 사용자가 외부 문서에 직접 붙여넣어 게시 |
| 명시적 제외 | 외부 문서 서비스 게시 실행과 게시 이력, Word 파일 편집 |
| 이번 문서의 설계 제안 | Tauri와 Rust, 단일 작성자, 로컬 저장, 작업별 대화, 변경 제안의 분리 보관 |
| 실제 확인이 필요한 사항 | 사용자 PC의 CLI 실행과 계정 권한, 계정 이용 정책, macOS 세부 지원 범위, 붙여넣기 호환성 |

현재 공식 안내는 Claude 플랜으로 로그인한 CLI의 프로그램 호출도 구독 한도를 사용할 수 있다고 설명한다. 따라서 API credits 활성화를 이 제품의 선행 조건으로 두지 않는다. 구독 한도, 계정 이용 정책 및 향후 정책 변경은 여전히 적용된다. [S1]

## 2 문서 묶음의 읽는 순서

| 문서 | 답하는 질문 |
| --- | --- |
| 기획서 PRD | 누구의 어떤 문제를 풀며 첫 출시에서 무엇을 제공하는가 |
| 기능 명세 SPEC | 각 화면과 버튼은 어떤 상태에서 어떻게 동작하는가 |
| 개발 설계서 DEV | 저장, 승인 검증, CLI 연동과 복구를 어떻게 구현하는가 |

SPEC의 동작 규칙을 기능 구현의 기준으로 삼는다. DEV의 기술 선택은 구현 제안이며, 실제 검증 결과에 따라 바꾸되 SPEC의 사용자 보장은 유지한다.

## 3 핵심 사용자와 유저 스토리

주 사용자는 메모, 여행 안내, 학습 자료 등 Markdown 문서를 작성하고 다듬는 사용자다. MVP에서는 한 사람이 작성과 검토를 모두 수행한다고 가정한다. 여러 사람의 승인 절차와 실시간 공동 편집은 포함하지 않는다.

**대표 작업:** 여행 준비 가이드의 특정 문단을 더 명확하게 고치도록 요청한다. 변경 세 건 중 한 건은 승인하고 한 건은 거절한다. 나머지 한 건에는 코멘트를 달아 다시 제안받는다. 다음 날 같은 작업을 열어 이어서 검토한 뒤 확정본을 복사한다.

| ID | 사용자의 필요 | 제공할 행동과 결과 |
| --- | --- | --- |
| US01 | 원본을 잃지 않고 시작하고 싶다 | 새 문서 또는 .md 가져오기, 최초 버전 생성 |
| US02 | 원하는 부분만 고치고 싶다 | 선택 영역, 현재 섹션, 문서 전체 범위 지정 |
| US03 | 무엇이 바뀌었는지 정확히 알고 싶다 | 인라인·나란히 diff, 삭제·추가 줄과 바뀐 표현, 문맥 확장, 변경 간 이동 |
| US04 | 마음에 드는 부분만 쓰고 싶다 | 변경 단위 승인과 거절, 독립성이 없는 변경은 묶어 처리 |
| US05 | 제안 방향을 바로잡고 싶다 | 문단 또는 제안에 코멘트, 재제안, 제안 직접 수정 |
| US06 | 만족한 결과를 빨리 반영하고 싶다 | 현재 제안 묶음의 남은 변경 전체 승인 |
| US07 | 문서 방향을 바꾸며 시도하고 싶다 | 전체 재작성안 비교, 적용 또는 취소, 적용 후 복원 |
| US08 | 다음 날 이어서 하고 싶다 | 확정본, 대화, 코멘트, 제안, 고정 조건 복원 |
| US09 | 설명만 듣고 싶을 때가 있다 | 설명 요청은 문서 변경 제안을 만들지 않음 |
| US10 | 작업을 잃지 않고 다시 시도하고 싶다 | 중단, 오류 구분, 재시도, 자동 저장과 충돌 안내 |
| US11 | 결과를 다른 편집기에 쓰고 싶다 | 확정본 미리보기, Markdown 복사와 .md 저장 |

**추가할 가치가 높은 기능:** 고정 조건, 요청 범위, 설명과 수정의 구분, 자동 저장, 작업 재개, 외부 파일 충돌 감지는 MVP에 포함한다. 이 기능들은 버튼의 수를 늘리기보다 잘못된 변경과 반복 설명을 줄이는 역할을 한다.

## 4 제품 범위

- Markdown 파일 열기·생성·원문 편집·미리보기
- 작업별 목표·고정 조건·요청 범위·대화 보관
- 인라인/나란히 diff·부분 승인·거절·남은 제안 전체 승인
- 후보 직접 수정·코멘트·재제안·전체 재작성 비교
- 자동 저장·버전 복원·재시작 후 작업 재개·외부 파일 충돌 처리
- 공식 CLI 연결 진단·요청 중단·사용자 재시도
- 저장된 확정본 Markdown 복사·파일 내보내기

참고 내용을 요청에 직접 붙여넣을 수 있지만 PC 전체나 폴더를 자동 수집하지 않는다.

**범위 밖:** 외부 문서 서비스 연결 계정·게시·게시 이력·페이지 동기화, 실시간 공동 편집, 다중 사용자 승인, 클라우드 동기화, 브랜치 관리, Word/HWP 편집, 서식 포함 HTML 복사, 문서 사실 검증. 로컬 문서 버전은 외부 게시 이력과 구분한다.

## 5 안전성 기준

미승인 제안은 확정본이나 내보내기에 포함하지 않는다. 저장 완료한 버전과 검토 상태는 재시작 후 복원하며 충돌·실패를 조용히 덮어쓰지 않는다. 확정본과 예상본, 부분 승인과 전체 재작성, 편집 취소와 버전 복원을 구분해 표시한다. 기대 동작은 [인수 기준](acceptance-criteria.md)과 [테스트 안내](../development/testing.md)를 따른다.

## 6 승인과 되돌리기의 제품 원칙

**전체 재작성에는 단순한 비교와 복원이 적합하다.** 다만 되돌리기만으로 승인 통제를 대신하지 않는다. 적용 전에는 원본과 재작성안을 비교하고 전체 적용 또는 취소한다. 적용 후에는 이전 버전으로 복원할 수 있게 한다. MVP에 복잡한 브랜치 화면은 넣지 않는다.

**전체 승인은 필수다.** 화면의 버튼은 모호한 전체 승인 대신 “남은 변경 N개 승인”으로 표시한다. 범위는 현재 문서의 현재 제안 묶음이다. 거절하거나 교체된 제안은 포함하지 않는다. 충돌이 있으면 하나도 적용하지 않고 해결 방법을 안내한다.

| 사용자가 하려는 일 | 제공 기능 | 보존 규칙 |
| --- | --- | --- |
| 아직 반영하지 않은 제안을 버림 | 제안 취소 | 확정본 유지, 이미 승인한 변경은 유지 |
| 방금 직접 입력한 글을 되돌림 | 편집 취소와 다시 실행 | 현재 편집 구간 안에서만 동작 |
| 승인 또는 전체 적용을 되돌림 | 버전 기록에서 복원 | 현재 상태를 보관하고 새 버전을 생성 |

작업 히스토리는 “대화 로그 전체를 과거로 돌리는 기능”이 아니다. 문서를 복원하면 다음 AI 요청에 복원된 확정본과 복원 사실을 전달한다. 지난 대화는 맥락으로 남기되 최신 확정본을 우선한다.

## 7 제안의 검토 단위

부분 수정에서는 문장이나 문단의 독립적인 변경을 검토 단위로 삼는다. 제목 이동, 섹션 재배열, 설명 간 전제 변경처럼 함께 적용해야 의미가 유지되는 변경은 한 그룹으로 승인한다. 문서 구조 전체가 바뀌면 전체 재작성 모드로 전환한다.

거절과 코멘트는 역할이 다르다. 거절은 해당 제안을 반영하지 않는 결정이고, 코멘트는 다음 제안의 방향을 정하는 요청이다. 거절 이유는 선택 입력이며, 사용자가 남긴 이유는 해당 작업의 맥락에 보관한다.

**예상 흐름:** 문서 선택 → 작업 목표와 고정 조건 → 수정 범위 지정 → AI 제안 → 비교와 코멘트 → 부분 또는 전체 승인 → 확정본 확인 → 복사 또는 저장. 앱 종료 후에는 마지막 작업과 미승인 제안으로 돌아온다.

## 8 기본 작업 화면

![S01 문서 편집과 작업 대화 화면](../design/assets/screens/S01_editor.png)

**S01 기본 화면.** 왼쪽에서 문서와 작업을 선택하고, 가운데에서 확정본을 편집하거나 변경을 비교한다. 오른쪽에는 해당 작업의 대화와 고정 조건을 둔다. 화면은 예시이며 문구와 배치는 사용성 검증에서 조정할 수 있다.

1. 확정본 버전과 저장 상태를 항상 표시한다. AI가 제안을 생성하는 동안 확정본으로 오인할 내용은 섞지 않는다.
2. 선택 영역이 있으면 범위를 자동 제안하되 사용자가 실행 전에 확인할 수 있게 한다. 요청 후 범위를 조용히 확대하지 않는다.
3. “설명만 요청”과 “수정 요청”을 구분한다. 설명 응답은 문서에 자동 삽입하지 않는다.
4. 고정 조건은 편집 가능한 짧은 목록이다. 대상 독자, 문체, 유지할 용어와 수치 등을 넣는다.
5. 연결 상태는 사용 가능, 로그인 필요, 한도 또는 정책 제한 등 확인된 상태만 표시한다. 정확한 잔여 구독량을 추정해 보여주지 않는다.

창 폭이 좁아지면 왼쪽 목록과 오른쪽 대화를 접을 수 있게 한다. 권장 최소 창 크기는 1280×800이며 실제 가독성은 대상 OS와 배율에서 검증한다.

## 9 부분 승인과 코멘트 화면

![S02 변경 검토와 코멘트 화면](../design/assets/screens/S02_inline_diff.png)

**S02 인라인 diff.** 실제 원문에서 삭제되는 줄과 후보에 추가되는 줄을 같은 읽기 흐름으로 보여준다. 변하지 않은 문맥도 함께 표시하며, 문장 내부에서 바뀐 표현은 더 진하게 강조한다. 행 번호와 −/+ 기호를 병행하고, 변경별 승인·거절·코멘트를 가까이 둔다.

![S03 나란히 diff](../design/assets/screens/S03_split_diff.png)

**S03 나란히 diff.** 왼쪽은 현재 확정본, 오른쪽은 유효한 미승인 제안을 반영했을 때의 예상본이다. 넓은 비교 공간이 필요하면 대화 패널을 접는다. 오른쪽을 보는 것만으로 파일이 바뀌지 않는다. 소스 차이를 기준으로 검토하고, 서식을 적용한 읽기 화면은 미리보기에서 확인한다.

화면 위의 “남은 변경 N개”는 승인 단위의 수이고 “추가/삭제 N줄”은 줄 diff 통계다. 둘을 같은 수치로 취급하지 않는다. 변경 전체가 독립적이지 않으면 하나의 승인 그룹으로 표시한다.

1. 변경 요약은 검토를 돕는 정보다. AI의 설명이 실제 변경 내용과 다르면 실제 차이를 기준으로 판단한다.
2. “이 변경 다시 제안”은 선택한 변경과 코멘트를 대상으로 한다. 기존 제안은 기록에 남고 새 제안은 미승인 상태로 시작한다.
3. 제안 문구를 직접 고쳐도 확정본은 바뀌지 않는다. 수정된 제안을 승인할 때 반영한다.
4. “남은 변경 N개 승인”은 대상과 제외 항목을 보여주는 확인창을 거쳐 현재 묶음에만 적용한다. 적용 전에 전체 유효성을 확인하고 하나의 버전으로 저장한다.
5. 생성 중 사용자가 본문을 수정했다면 이전 기준으로 만든 결과에 “최신 문서와 비교 필요”를 표시한다. 바로 승인할 수 없다.

한 변경에 여러 코멘트를 남길 수 있지만 MVP에서는 사용자와 AI 사이의 작업 코멘트만 지원한다. 다른 사람을 태그하거나 알림을 보내는 기능은 제공하지 않는다.

## 10 전체 재작성 화면

![S06 전체 재작성안 비교 화면](../design/assets/screens/S06_full_rewrite.png)

**S06 전체 재작성.** “다른 방향도 보여줘”, “전체적으로 더 명확하게 작성해줘”처럼 문서의 구조와 논리가 크게 바뀌는 요청은 하나의 재작성안으로 비교한다.

1. 사용자는 기준 확정본과 새 재작성안을 함께 볼 수 있다. 변경 개요와 제목 구조의 변화도 확인한다.
2. “이 재작성안 적용”은 문서 전체를 한 번에 반영하며 적용 직전 버전을 자동 보관한다.
3. “제안 취소”는 재작성안을 닫고 현재 확정본으로 돌아온다. 취소한 내용은 작업 기록에서 확인할 수 있다.
4. “다른 방향 요청”은 현재 보고 있는 제안을 바탕으로 다시 작성한다. 어떤 제안을 대상으로 하는지 대화에 표시한다.
5. 이전 안은 간단한 목록으로 볼 수 있다. 과거 안을 다시 선택해도 최신 확정본을 기준으로 재검증한 후 적용한다.

부분 제안이 남아 있는 상태에서 전체 재작성을 시작하면 “이전 제안을 기록으로 옮기고 확정본에서 재작성”이라는 행동을 표시한다. 실행은 이 전환을 포함한다. 기존 미승인 제안을 조용히 섞지 않는다.

복원은 전체 적용과 함께 제공되어야 한다. 단순히 마지막 AI 응답을 다시 보여주는 기능은 문서 복원을 대신할 수 없다.

## 11 버전 기록과 작업 연속성

![S07 버전 기록과 복원 화면](../design/assets/screens/S07_restore.png)

**S07 버전 기록.** 사용자는 각 버전의 생성 이유를 보고 현재 문서와 비교한 뒤 복원한다. 복원 전 상태도 남기므로 다시 돌아갈 수 있다.

**문서 기억과 대화 기억을 함께 관리한다.** 앱은 현재 확정본, 작업 목표, 고정 조건, 승인·거절 결정, 코멘트와 작업 대화를 로컬에 보관한다. Claude 세션 재개 기능과 별도로 이 정보를 관리한다. 긴 대화에서는 요약이 사용될 수 있으며 모든 대화를 무제한 기억한다고 약속하지 않는다.

- 같은 문서의 같은 작업을 열면 대화와 미완료 검토를 이어서 제공한다.
- 새 작업은 독립적인 목표와 대화를 가진다. 문서 공통 조건은 상속하되 작업별 지시는 분리한다.
- 세션이 없어지면 저장된 맥락으로 새 세션을 만들고 “저장된 작업 맥락으로 다시 연결”이라고 알린다.
- claude.ai의 기존 대화 내용을 자동으로 가져오는 기능은 포함하지 않는다.

문서 파일만 다른 PC로 옮기면 내용만 이동한다. 대화와 검토 상태를 다른 PC까지 옮기는 기능은 MVP 범위가 아니다. 로컬 버전 이력은 PC 장애에 대비한 외부 백업을 대체하지 않는다.

## 12 지원 범위와 제한

목표 환경은 macOS 14 이상·Apple Silicon·로컬 디스크다. 문서 크기는 UTF-8 1 MiB, AI 입력 맥락은 합계 200 KiB, 검증 응답은 합계 2 MiB로 제한한다. CLI의 모델 한도가 더 작을 수 있으며 앱이 범위를 조용히 잘라내지 않는다.

공식 CLI 정책·버전·구독 한도, 문서와 DB의 저장 일관성, 외부 파일 변경, 큰 재작성의 가독성과 대화 맥락의 한계는 사용자 안내와 오류 처리에서 구분한다. 지원 환경·설치는 [설치 안내](../installation.md), 검증 경계는 [테스트 안내](../development/testing.md#검증-범위와-한계)를 따른다.

## 14 검토 화면의 설계 근거

VS Code의 인라인·나란히 diff와 변경 간 이동, GitHub의 변경 줄 코멘트, Google Docs의 제안 승인과 전체 승인, Obsidian의 원문 편집·읽기 화면 분리를 참고했다. 제품 화면을 복제하지 않고 문서 작성자에게 필요한 행동을 선택했다. Git 저장소·commit·PR 용어는 사용자 작업 흐름에 넣지 않는다. 근거와 채택 범위는 [참고 자료](../references.md)에 정리했다.

사용성 검증에서는 “모호한 문장 개선”을 요청했는데 AI가 준비물 확인 시간을 10분에서 5분으로 바꾼 예시를 사용한다. 작성자가 실제 diff에서 이를 발견하여 거절할 수 있는지 확인한다. 고정 조건이 있다고 모델이 반드시 준수한다고 가정하지 않는다. 이 예시는 확정본에 잘못된 수치가 들어가지 않도록 검토하는 필요성을 보여준다.

화면을 보고 답할 수 있어야 할 질문은 현재 확정본이 무엇인지, 어느 표현이 삭제·추가되는지, 이 버튼이 어떤 변경을 반영하는지, 코멘트 후 새 제안을 다시 승인해야 하는지, 적용 후 어디서 복원하는지다. [시나리오 문서](../design/scenarios.md)는 이 질문을 사용자 행동과 화면 상태로 연결한다.
